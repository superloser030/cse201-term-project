# 설계 결정 기록 (Design Decisions)

spec(CSE201 Term Project v1)에 명시되지 않았거나 해석이 갈리는 부분에 대해 팀이 정한 내용입니다.
보고서의 "가정(assumption)" 항목에 그대로 사용할 수 있습니다.

- 기준 문서: `(release) 2026-fall-cse201-term project - v1.pdf`, `sample test routine.pdf`
- 근거 종류
  - **spec 명시**: spec에 적힌 그대로 따름
  - **spec 애매**: spec에 언급은 있으나 해석이 갈려 팀이 해석을 정함
  - **spec 없음**: spec에 언급이 없어 팀이 정함
  - **실제 ATM**: 실제 ATM의 일반적 동작을 참고함 (공식 자료로 확인한 것은 아님)
- 기본 방향: spec이 정하지 않은 부분은 **최대한 실제 ATM 동작**을 따른다.

---

## 1. 관리자 거래 내역 범위
- **결정**: 관리자 카드를 넣은 **그 ATM**에서 일어난 **모든 사용자(은행 무관)의 성공 거래**를 표시한다.
- **spec**: REQ7.2 "시스템 시작 이후 모든 사용자의 모든 거래" / 7번 설명 "ATM의 관리자"
- **근거 종류**: spec 애매 + 실제 ATM (ATM은 자기 기기에서 처리한 거래를 은행 구분 없이 기록함)

## 2. 관리자 카드 소속과 사용 범위
- **결정**: 은행마다 관리자 카드 1장. 그 은행이 **주거래 은행인 ATM에서만** 사용 가능 (Multi ATM도 동일).
  다른 은행의 관리자 카드를 넣으면 Invalid Card 처리 후 session 종료.
- **spec**: 용어 정의 "**은행 관리자**가 ATM에 접근할 때 쓰는 특수한 종류의 카드" / 7번 설명 "ATM의 관리자" / 시스템 설명 "각 ATM은 주거래 은행이 관리"
- **근거 종류**: spec 애매(강한 추정) + 실제 ATM

## 3. 관리자 카드 번호
- **결정**: `ADMIN-<은행 이름>` 형식으로 입력 파일의 은행마다 자동 생성 (예: `ADMIN-Kakao`, `ADMIN-IM`).
  프로그램 시작 시 화면에 출력하지 않는다. 규칙은 README와 보고서에 적는다.
- **spec**: 관리자 카드 번호 형식, 생성 방법 언급 없음. 입력 파일에도 관리자 카드 없음.
  REQ1.11의 하드코딩 금지 대상은 "계좌와 ATM 정보"이므로 관리자 카드 규칙을 코드에 두는 것은 금지 대상이 아님.
- **근거 종류**: spec 없음
- **영문으로 정한 이유**: 입력 파일의 일반 카드 번호(숫자)와 겹칠 위험이 사실상 없음.

## 4. 관리자 카드 비밀번호
- **결정**: 없음. 관리자 카드를 넣으면 바로 관리자 메뉴("Transaction History"만)로 이동.
- **spec**: REQ7.1에 비밀번호 언급 없음. 비밀번호 정의는 "카드와 **계좌**에 연결된 비밀번호"인데 관리자 카드에는 계좌가 없음.
- **근거 종류**: spec 없음

## 5. 카드 구조
- **결정**: `Card`(abstract) → `UserCard` / `AdminCard` 상속 계층.
- **spec**: 용어 정의에서 관리자 카드는 "특수한 **종류의** 카드" (is-a 관계). 카드 종류는 일반 카드와 관리자 카드 2가지만 정의됨.
  관리자 카드도 일반 카드처럼 카드 번호를 콘솔에 입력해서 넣음 (화면 요구사항 + REQ7.1).
- **근거 종류**: spec 명시(종류 정의) + 설계 결정

## 6. 입력 파일 이름
- **결정**: 프로그램 시작 시 파일 이름을 입력받는다. Enter만 치면 `sample_initial_condition.txt`.
  파일을 열 수 없으면 오류 메시지 출력 후 **파일 이름을 다시 묻는다**.
- **spec**: spec 예시 `sample_initial_condition.txt`, spec 본문 다른 곳 `initial_condition.txt`,
  test routine `initial_conditions.txt`로 이름이 서로 다름. test routine은 demo 때 초기 조건 파일을 제공한다고 명시.
- **근거 종류**: spec 애매 (demo 대응)

## 7. 입력 파일 내용 검사
- **결정**: 아래 문제가 있으면 **어떤 문제인지 오류 메시지 출력 후 프로그램 종료** (fail-fast).
  - 카드 번호 중복 (관리자 카드 `ADMIN-<은행>` 포함)
  - 계좌번호 중복
  - ATM 일련번호 중복
  - 은행 이름 중복
  - 계좌/ATM의 은행 이름이 은행 목록에 없음
  - 읽기 실패 (숫자 자리에 글자, 줄 수 부족 등)
  - ATM 종류/언어 값이 `Single`/`Multi`, `Unilingual`/`Bilingual`이 아님
- **spec**: 용어 정의 "계좌번호: 고유", REQ1.1 "일련번호: 모든 ATM 중 고유". 카드 번호 고유성은 명시 없음
  (ATM이 카드 번호로 계좌를 찾으므로 고유해야 동작함). 입력 파일 오류 처리는 언급 없음.
- **근거 종류**: spec 명시(일부) + spec 없음 + 실제 시스템 관행 (unique constraint, fail-fast)

## 8. 출금 시 지폐 50장 제한
- **결정**: 적용. 요청 금액을 내주는 데 50장을 넘게 필요하면 오류 → session 종료.
- **spec**: 화면 요구사항 "한 번에 **넣거나 내줄 수 있는** 지폐는 최대 50장"
- **근거 종류**: spec 명시

## 9. 출금 500,000원 한도와 수수료
- **결정**: 한도에 수수료 **미포함**. 실제로 내주는 현금 금액 기준.
- **spec**: REQ5.7 "거래 1회당 최대 **현금 출금액**은 500,000원"
- **근거 종류**: spec 애매(표현이 미포함 쪽을 뒷받침) + 실제 ATM

## 10. 입금 시 지폐 50장 제한과 수수료 지폐
- **결정**: 입금 지폐 + 수수료 지폐를 **합쳐서** 50장 이하.
- **spec**: 4번 설명 "**거래 1회당** 입금 가능 지폐 50장" / REQ4.4 "입금액과 수수료는 따로 입력"
- **근거 종류**: spec 애매 + 실제 ATM (거래 1회 단위로 임시 보관함(escrow) 용량 한도가 있음)

## 11. 수수료로 넣은 현금이 수수료와 다를 때
- **결정**: 오류 메시지 → 그 거래에서 넣은 현금 **전부 반환** (ATM 현금, 계좌 모두 반영 안 함) → session 종료.
- **spec**: REQ4.4는 따로 입력하라고만 함. 틀린 경우 처리는 없음. REQ9.1 "예외 시 오류 메시지 후 session 종료"
- **근거 종류**: spec 명시(REQ9.1) + 실제 ATM (처리할 수 없는 투입금은 반환, 거스름돈 기능 없음)
